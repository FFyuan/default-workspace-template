A background pass whose base moved before it could land is now caught up instead of thrown away. When another chat commits while an update-self, update, heal or critical-app worker runs, the lead keeps the worker and asks it to merge the current `HEAD` into its branch. The worker resolves any conflict there, regenerating lockfiles rather than picking a side. It hardens what came in that touches a creation in the pass and re-runs its test gate over what the catch-up changed for the pass, from a scope file written for the catch-up alone (`pass-scope --diff-base <its tip before the merge> --lead-ref <the lead's HEAD>`, then `select-tests --scope-file`): the lead's commits that touched a creation in the pass, every file both sides changed, what it committed afterwards, and the own suite of any creation in the pass that what came in reaches through something it depends on (a package, a `uv.lock` upgrade, a shared frontend package, or the root project's own `pyproject.toml` or `conftest.py` for a creation the root project collects). Other chats' commits in the same window no longer pull their suites into the gate. Then it reports `done` again. A pass over several creations is caught up the same way, and a note naming a creation the pass does not cover makes it stale too: the catch-up adds that creation to the pass, and the lead records it in its own task file and in the ticket's title, so a chat taking the pass over leads it with that creation and another chat's single-flight check finds the pass by it. Before, every such case discarded the finished pass and dispatched a new one from scratch; for update-self that meant redoing a roughly 40-minute validation because of an unrelated commit. A fresh pass now replaces a stale one only when its worker is gone, or when no chat that can receive its reports is left to lead it.

update-self in particular: before the apply, the lead waits for other chats' in-progress edits (a dirty tree, or another chat's `editing service` lease) to settle instead of refusing. It then checks whether the worker's branch still fast-forwards, and catches the worker up if not, messaging it through the chat app's `message_chat.py` where the workspace has it, or `mngr message --start` otherwise, so a worker that stopped while it waited is started rather than replaced. The worker guide has a new §7 for the catch-up. The catch-up merge must not carry an `update-self:` subject, and the worker does not re-run its full 4b selection, which would re-select the whole pass. The exit-1 guidance in SKILL.md, `apply-outcomes.md` and the apply's own refusal message now say to catch the worker up rather than re-dispatch, and never to destroy the waiting worker. The old instruction to re-dispatch is what led a lead to destroy a finished, validated worker.

A pass whose holder chat stopped while its worker is still there (for example, waiting days on a gate nobody relayed) is now taken over by the next chat as its lead: it reassigns the ticket and relabels the worker as its own, acts on the last report the gone holder read (answering a gate, or relaying it to the user when it is theirs; merging a `done`; or handling a `no-update-needed` or `stuck`), and drives the pass to the end. Before, such a pass fit neither "live" nor "abandoned", and the only written way to take it over destroyed it.

Superseding a pass whose worker is gone no longer deletes the work it left behind. `create_worker.py destroy --delete-branches` now refuses, before destroying anything, while a branch it would delete holds commits that neither `HEAD` nor any other local branch has, and prints a `git branch superseded/<name> <branch>` command that keeps each one; `--discard-unmerged` overrides it. The lead keeps those branches, names them in the new pass's task under `## Carried work`, and tells the user. The new worker merges them into its own branch and hardens them as part of the change. Before, the documented takeover would have deleted two finished, tested fixes on an abandoned pass's branch.

A milestone the lead provisionally merged and then reverted is brought back by the worker on its own branch, as a revert of the lead's revert, and reaches the lead again only with the worker's next merged report. Before, the lead re-applied it on its own branch, the served tree, before a catch-up or the final merge, which put the work the user had rejected back in front of them for the whole catch-up.
