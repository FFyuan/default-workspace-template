A harden pass now covers a change, not a creation. `update-creation` and `heal-creation` dispatch one pass, with one worker, for every creation the change in the chat touched (or, for an emergent update or a heal, every creation the gap or failure spans): two apps edited to work together, or an app and the skill that drives it, are one pass instead of one worker per app. The pass is named by `$SLUG` (the creation's name when there is one, otherwise a short name for the change), its ticket title lists every creation it covers, and the single-flight check and the go-live run for each creation. Whether to split the pass is the worker's call, by job rather than by creation.

A task file names its creations in `creations`, a space-separated list of `<type>:<name>` (`app:roadmap skill:sync-roadmap`; the types are `app`, `skill`, `service`, and `shared` for a script or reference under `.agents/shared`), and carries one `scope_file` for the pass. `crystallize-creation` names its one creation the same way. `parse_task_frontmatter.py` refuses a task that names an `operation` without `creations` and `scope_file`, or with a leftover top-level `type`; `pass-scope`, the first command the worker runs on them, refuses a malformed creation, or one named twice (also when an app is named by both its registered name and its package directory). The generic worker computes the pass's footprint with the new `app-manifest pass-scope` (one command, every creation, one diff judged against all of them), loads a `type-<TYPE>.md` per type among its creations, and writes one final-gate block per creation; the lead's freshness check runs the same command. The worker's stale `system-interface` type is gone.

A change that touches a critical app takes `update-app`'s careful flow as a whole: an ordinary app, skill, or service the same change touches is edited and previewed in the same worktree, hardened by the same pass, and landed by the same apply. After the apply, the lead checks that the ordinary ones work and fixes what doesn't. `update_self.py apply --keep-rollback-point` now takes `--pass-scope <file>`, the pass's `app-manifest pass-scope` output, and the kept rollback point records the pass's other apps and services from it: the notice names its apps, and a rollback restarts the programs its wiring names. A pass creation with no program to restart (a service a routine runs, say) is named in the rollback's outcome for the agent rather than stopping the rollback. Only the critical apps gate the rollback's verdict, as they gate the apply's: an ordinary app or service that does not come back is the agent's to fix, not an emergency.

`update-creation`'s and `crystallize-creation`'s go-live for an app now says to refresh its window and for a service to restart its programs; they previously told a service to refresh a window it does not have.

The harden test gate now selects from what the pass is responsible for, not from everything that landed on the shared branch since `diff_base`. Other chats' commits in that window used to bring in their suites: a reading-room takeover ran the chat and shell suites and the full root suite for about 470 unrelated commits. The worker writes its scope file with `--lead-ref` (the lead's `HEAD`) and runs `app-manifest select-tests --scope-file`, which selects the files the pass's footprints account for, every file the worker's own branch changed, and every file of a commit before the fork that touched a creation in the pass (the change being hardened). Other chats' files land in the scope file's `others` instead, so they no longer show up in `Outside footprint:` either.
