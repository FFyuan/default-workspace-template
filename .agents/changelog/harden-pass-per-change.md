A harden pass now covers a change, not a creation. `update-creation` and `heal-creation` dispatch one pass, with one worker, for every creation the change in the chat touched (or, for an emergent update or a heal, every creation the gap or failure spans): two apps edited to work together, or an app and the skill that drives it, are one pass instead of one worker per app. The pass is named by `$SLUG` (the creation's name when there is one, otherwise a short name for the change), its ticket title lists every creation it covers, and the single-flight check, the merge-time freshness check, and the go-live run once per creation. Whether to split the pass is the worker's call, by job rather than by creation.

The task file names its creations in a `creations` list, one entry each with a `name`, a `type`, and a `scope_file` where the creation has a footprint (`scope-<name>.json` beside the task file). `crystallize-creation` writes a one-entry list. `parse_task_frontmatter.py` validates the list, refuses a task that names an `operation` without one, and emits `CREATION_COUNT` plus numbered `CREATION_<i>_NAME`, `CREATION_<i>_TYPE`, and `CREATION_<i>_SCOPE_FILE` variables. The generic worker loads a `type-<TYPE>.md` once per type among its creations, writes a scope file per creation, settles `outside_footprint` against the union of their footprints, and writes one final-gate block per creation.

A change that touches a critical app takes `update-app`'s careful flow as a whole: an ordinary app or skill the same change touches is edited and previewed in the same worktree, hardened by the same pass, and landed by the same apply. The update apply's kept rollback point now records every app whose files the merge changed, critical or not, so rolling back from the notice restarts (and the banner names) an ordinary app that rode along.

`update-creation`'s go-live for an app now says to refresh its window and for a service to restart it; it previously told a service to refresh a window it does not have.
